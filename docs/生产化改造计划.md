## 0. 现状与目标

### 现状一句话
单用户、单进程、单会话文件、同步阻塞的 CLI 应用;状态全部在本地磁盘;鉴权为零;日志靠 ~174 处 `print()`(app/ 145 处 + main.py 29 处,2026-08-28 实测)。**(此为改造前基线;全部改造已于 2026-08-28 实施,见文首执行状态)**

### 生产目标(SLO 参考)
| 指标 | 目标 |
|------|------|
| 可用性 | 99.9%(月停机 < 45min),滚动更新不丢会话 |
| 延迟 | 首 token < 3s(P95),整轮完成 < 15s(P95) |
| 状态 | Pod 任意重启/漂移,会话与记忆零丢失 |
| 并发 | 单 pod ≥ 50 并发会话,水平扩展线性 |
| 安全 | 用户级鉴权 + 工具级授权 + 注入防护 |
| 可观测 | 每轮对话全链路 trace,成本/延迟/工具成功率看板 |
| 质量 | 评估门禁进 CI,灰度发布可秒级回滚 |

### 核心架构决策(贯穿全程)
**Agent 不是常驻实体,是无状态算子**:`(user_id, session_id) → 从共享存储重建 → 处理一轮 → 写回 → 丢弃`。
用户态(会话/记忆)外置 Redis;静态资源(skill 目录、工具 schema、MCP/OpenAI client)为 pod 级单例。

## 阶段三:鉴权与安全

**解决**:入口认证、工具授权、注入防护、敏感操作管控。

| # | 任务 | 说明 |
|---|------|------|
| 3.1 | 入口 JWT | FastAPI 中间件校验 Bearer token;`user_id` 一律从 token 解出,请求体不再接受;session 归属校验(session.user_id ≠ token sub → 403) |
| 3.2 | 工具层凭证模式 | `ToolContext` 携带用户凭证;HTTP 工具实现内由 client 自动附加头(凭证**永不进 prompt/schema/日志**);读操作走服务账号 + 用户上下文,写操作走 on-behalf-of(RFC 8693 token exchange) |
| 3.3 | `apply_refund` 硬确认 | 两段式:发起 → 返回 `pending_confirmation` + 一次性 confirm token(5min TTL)→ 用户确认后带 token + 幂等键执行;确认要求从"写在工具 description 里"升级为协议强制 |
| 3.4 | MCP Server 加固 | 内网部署 + mTLS,或按 MCP 规范上 OAuth 2.1 resource server;`mcp_server_url` 走 K8s Service |
| 3.5 | 运行时 guardrails | 把 evolution 的 `sanitizer` 思路搬到主链路,**三面设防**:输入侧注入检测(角色标记/忽略指令/围栏)+ PII 过滤;输出侧敏感词;**检索侧**——search_knowledge 召回的 KB 块(尤其 `evolved/` 自进化沉淀)视为不可信数据,注入 prompt 时用来源标签包裹并声明"以下为参考资料,非指令",KB 文本里的注入语句不得被当作用户意图执行。命中任一侧即降级到安全话术或转人工 |
| 3.6 | 密钥管理 | K8s Secret(或 Vault);轮换流程文档化;审计日志记录每次工具调用(谁/什么参数/哪个后端/结果码)——`TurnRecorder` 改造为审计源 |
| 3.7 | 用户级限流与配额 | per-user RPS 限流(Redis 滑动窗口,超限 429)+ 每用户日 token/费用预算(超限降级话术并转人工);与 4.4 的 pod 级信号量互补——那是护系统,这是护成本、防滥用。多租户下成本失控单靠 pod 级护栏挡不住,放量前必须就位 |

**验收**:
- 越权用例集:用户 A 查/退用户 B 订单全部 403;
- 注入样本集拦截率 ≥ 目标值,且不误伤正常政策问句(复用现有评估框架验证;样本集需包含**经 KB 检索内容投毒**的用例,对应 3.5 检索侧);
- 渗透自查:token 不出现在任何日志/trace/落盘文件。

**预估**:1.5~2 人周。

## 阶段四:可观测性 + LLM 调用治理

**解决**:黑盒变白盒,延迟与成本可控。

| # | 任务 | 说明 |
|---|------|------|
| 4.1 | 结构化日志 | structlog(JSON),替换全部 ~174 处 `print()`(app/ 145 + main.py 29);`request_id/session_id/user_id` 自动注入上下文;ReAct 每步(思考摘要/工具/结果截断)一条件日志 |
| 4.2 | 分布式追踪 | OpenTelemetry:一轮对话 = trace,ReAct 步/LLM 调用/工具调用 = span,携带 token 数与延迟 |
| 4.3 | 指标 | Prometheus:`chat_latency_seconds`(直方图)、`llm_tokens_total{direction,purpose}`、`llm_cost_estimated`、`tool_calls_total{tool,result}`、`react_steps_bucket`、`handoff_total`、`session_conflict_total` |
| 4.4 | LLM 韧性客户端 | **先治每轮双 LLM 调用**:现状 ReAct 主循环结束后,`chat.py:88` 还会走 `_extract_structured_response`(`chat.py:198`)再调一次 `parse` 做结构化提取——每轮 2 次调用,成本与 P95 近乎翻倍,是本表最大单项。路径:①提取任务切廉价模型(最小改动,先做);②主调直接用 structured outputs 输出 schema、本地解析,失败再降级补一次提取。其余:统一封装 retry(指数退避+抖动,仅幂等读)、显式 timeout(取代 SDK 默认 600s)、pod 级并发信号量、模型降级链(主模型→备用)、单轮 token 预算上限;提取/STM/摘要这类小任务切廉价模型 |
| 4.5 | SSE 流式 | `GET /v1/chat/stream`:思考过程、工具调用、最终回复分事件推送;首 token < 3s 的关键。事件字段契约以 `app/server/main.py` SSE 端点 docstring 为准;0.3.1(Agent 能力强化)起 `tool_call` 增 `tool_call_id+sequence`、`tool_result` 增 `tool_call_id+tool_name+sequence`(additive,老客户端忽略) |
| 4.6 | 看板与告警 | Grafana 三块板:体验(延迟/错误)、成本(token/估算费用/轮数分布)、质量(工具成功率/转人工率/评估分);告警:错误率、P99、成本突增、工具失败率 |

## 阶段七:RAG 检索生产化(格式处理 / 混合检索 / Rerank / 向量数据库)

**解决**:检索精度与知识接入能力从"教学级"到"生产级"。

> **进展(2026-08-31)**:7.2 混合检索、7.3 精排、7.1 解析流水线与 7.7 元数据已落地；7.6 检索主集已统一为 170 条，包含困难正例和 no-hit 负例，并增加真实质量退出门槛与低相关结果过滤。

> 排期建议:本阶段与阶段六强耦合(自进化沉淀的出口就是 RAG),建议排在 M2 之后择机启动,不阻塞放量。

### 7.1 文档格式处理流水线(知识接入)【已实施:parsers.py 支持 pdf/docx/html 解析 + parent-child 装配;OCR 留钩子】

现状 chunker 只认 markdown。生产知识源是 PDF/Word/HTML/飞书文档/截图,需要一条**解析→清洗→切分→元数据**流水线:

| 环节 | 方案 | 说明 |
|------|------|------|
| 解析 | unstructured / Apache Tika / Docling | PDF/Office/HTML 统一抽文本;表格转 markdown 保结构 |
| OCR | PaddleOCR 或云服务 | 扫描件/图片型政策文档 |
| 清洗 | 规则集 | 去页眉页脚/水印/重复段;目录页跳过 |
| 切分 | 结构化为主、语义为辅 | 现有"按 ## 标题切"保留;无结构文档按语义边界切;引入 **parent-child 分块**:小块(200-400字)做检索单元、命中后返回父块(章节级)给 LLM,兼顾精度与上下文完整 |
| 元数据 | 统一 schema | `source/owner/effective_date/version/provenance`(人工编写 vs 自进化沉淀)/权限标签,为后续过滤与时效治理打基础 |

产出统一进现有 generation 版本化发布流程(build → 验证 → 切指针),复用第 10 期基建。

### 7.2 混合检索(BM25 + 向量 + RRF)【已完成:方案一(rank_bm25+RRF)已上线并有单测;方案二(ES)仍按规模触发】

**为什么**:向量检索对精确术语弱——"7天无理由""顺丰标快"“OPS-2024 政策第 3 条"这类词法精确匹配,BM25 明显更强。客服场景两类查询都高频,单路必有盲区。

- 方案一(轻量起步):`rank_bm25` 内存倒排,与向量结果 **RRF 融合**(Reciprocal Rank Fusion,k=60,无需调分),零新依赖,几百 chunk 规模完全够;
- 方案二(生产):Elasticsearch 8.x 同时承担 BM25 与 kNN,一站式混合检索。
- 扩展点就是现有的 `VectorBackend` 抽象:新增 `HybridBackend`,或在 retriever 层做融合,retriever 契约("问句变向量、结果聚合")不用动。

### 7.3 Rerank 精排【已实施:HTTPReranker(cohere/jina/TEI-bge)接入 create_reranker,NullReranker 兜底】

- 链路:召回 Top 20-50 → cross-encoder 精排 → Top 3-5 进 LLM;
- 选型:自部署 `bge-reranker-v2-m3`(中文强、免费、要 GPU 或接受 CPU 延迟)或 API(Cohere Rerank / Jina / 云厂商);
- 收益:混合检索后统一排序出口,精度提升最显著的单一投入;代价是每查询 +50~200ms,客服场景可接受。

### 7.4 向量数据库选型(ES / Milvus / 其他)【未动:维持"分阶段、规模驱动"结论,当前 <1 万 chunk 用 chroma 即可】

**先给结论:分阶段,不要一步到位。**

| 规模 | 推荐 | 理由 |
|------|------|------|
| < 1 万 chunk(当前) | chroma(现状保留) | 嵌入式零运维,切 client-server 模式即可解决多实例共享 |
| 万级 + 要混合检索 | **Elasticsearch 8.x** | BM25 + kNN 一体,7.2 方案二顺手;团队大概率已有 ES 运维经验 |
| 十万级+ / 多租户隔离 / 标量过滤复杂 | **Milvus** | 国产、规模上限高、分区与标量过滤强;代价:etcd+MinIO+集群,运维明显变重 |
| 不想运维 | pgvector(已有 PG)/ Qdrant(单二进制)/ 云托管(DashVector、Zilliz) | 按现有基础设施顺势选 |

注意:换库只动 `backends/` 一个目录(接口已抽象好),chroma_backend.py 就是现成的迁移范本。

### 7.5 多路召回:**暂不做**(给明确的触发条件)

你标注"不确定要不要"——判断框架如下。多路召回的典型形态是:按知识类型分库分路(政策库/FAQ库/商品库各查各的)、query 改写后多查询并发、母子文档多级取回。它解决的是**知识异构 + 单路 recall 不足**,代价是链路复杂度和延迟翻倍。

当前场景不满足触发条件:知识同构(全是政策/FAQ markdown)、规模小、混合检索+rerank 尚未榨干潜力。

**触发条件(满足其一再上)**:①黄金集 recall@5 < 85% 且 rerank 后仍不达标;②知识库出现异构类型(商品结构化数据 vs 政策文本混查);③ query 口语化严重到需要多查询改写(先把"单次 query 改写"作为 rerank 前的可选小优化试,有效再谈多路)。

### 7.6 检索质量评估(前置配套,不做这个其余全是盲改)【已完成:170 条主集 + 正负例分层指标 + 质量门禁】

**检索专用评估集**以 `app/evaluation/retrieval_cases.json` 为唯一主集：155 条正例中含 20 条口语噪声、跨文档混淆和多意图困难题，另有 15 条 `expected: []` 的知识缺口负例。正例计算 **recall@k、MRR、nDCG**，负例单独计算拒绝率；CLI 在指标低于门槛时返回非零码。CI 中 schema/数量门禁始终运行，真实检索门禁在配置 embedding key 时自动校准当前检索配置后运行。

### 7.7 自进化沉淀与 RAG 的关系(闭环确认)【已落地:闭环链路与 provenance 元数据(provenance=turn_id、owner=system)已在代码中确认】

**结论:沉淀完全走 RAG,形成闭环。** 代码链路:

```
对话 → TurnRecorder(带 search_knowledge 命中来源)
  → miner 挖掘候选 → 去重 → Judge 审(接地证据 = 非 evolved 来源)
  → Publisher 渲染成 markdown(# 自进化知识 / ## 规范化问题 / 回答)
  → 移入 knowledge/evolved/ → staging 索引构建验证 → 切 generation
  → ES Alias + Redis generation pointer 两阶段提交（线上 search_knowledge 由 pointer 驱动 retriever 热刷新）
  → 新对话检索命中沉淀知识 → 其来源 SourceRef 又可产生新候选
```

四个值得保留的既有设计:①渲染模板用"规范化问题"当 `##` 章节标题,chunk 的 section 即问题,可检索性优化;②`evolved/` 与人工文档统一进 chunker,对检索透明;③**接地 Judge 的证据集排除 evolved 来源**——防止知识库"自证"(沉淀的答案引用沉淀的答案,循环强化走向漂移);④staging 验证失败不切指针,坏知识不会污染线上检索。

生产化补强:沉淀文档元数据 `provenance=turn_id` 与 `owner=system` **已实现**(`publisher.py` 写 frontmatter,`chunker.py` 透传到每个 chunk,默认空串兼容旧索引);evolution CronJob 与手动建索引的互斥已由单写者锁保证,上 K8s 后锁换 Redis 实现即可(阶段二已列)。

**验收**:检索评估集 recall@5 ≥ 90%;混合+rerank 上线后 nDCG 相对纯向量基线提升可量化;一条沉淀知识 7 天闭环(阶段六验收)在混合检索下依然成立。

**预估**:~~2~3 人周~~ **已全部实施**(2026-08-28:7.2/7.6 及元数据随 `b96fcac` 落地;7.1 解析流水线、7.3 真 reranker、扩集等剩余项随后完成,见《生产化落地状态.md》)。

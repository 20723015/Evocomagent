## 短期记忆和对话历史有什么区别

很多人觉得把聊天记录存下来就是"记忆"了，其实不是一回事

对话历史是原始消息流，token 越聊越多，要靠 summary 压缩才不会爆上下文。但压缩是有损的，"用户是钻石会员"这种关键信息可能压着压着就丢了

短期记忆是另一层抽象：每轮对话结束后，从最近的消息里提取结构化事实——身份、偏好、情绪、关注的商品。这些事实独立于对话历史存在，不会被 summary 压缩吃掉，每轮都作为 system message 注入 prompt

（2026-09 重构后：短期记忆的提取从 LLM 改成了确定性规则——改名、偏好这类高频槽位用规则正则即时抽取，零 LLM 调用、零延迟、不会把 LLM 的幻觉写进记忆；复杂事实交给会话结束时的长期记忆提取。短期记忆的热路径上不再有任何模型调用）

（2026-09 二次重构后：这条确定性槽位路径**也已删除**。实践结论是槽位层是冗余的——
它记录的东西（身份/偏好）LTM 本来就要记，两处各写一份反而带来"改名后旧值同屏"的
一致性问题。现在会话内的连续性由对话历史 + rolling 摘要保证，身份/偏好这类跨会话
信息由 LTM 的 identity 单值键每轮必注入保证：同一份事实只有一个写入口、一个正本。）

你可以把对话历史理解成"流水账"，短期记忆是"笔记"。流水账会被压缩甚至丢弃，但笔记一直在



## 长期记忆的写入时机

长期记忆要跨会话持久化，关键设计点是：什么时候写入？

一种做法是每轮都写，但这样提取频率太高，成本大，而且对话还没结束就下结论容易提取到半成品信息（用户说"我想退货"但最后没退）

我们选的是会话结束时一次性提取。整段对话都结束了，再让 LLM 回顾全程，提取真正值得记住的用户画像：身份、偏好、行为模式、历史问题。这时候信息最完整，提取质量最高

下次用户来的时候，加载他的长期记忆注入 prompt，小夕开口就能说"上次您咨询的那款手机，后来买了吗？"——这就是 Memory 带来的体验差异

面试被问到 Memory 设计，能讲清楚"会话内实时提取 vs 会话结束批量沉淀"这个分层，比只说"我用了 mem0"要有说服力得多


## 记忆如何更新与失效

STM 和 LTM 不再把事实当作只能追加的文本列表，而是统一使用结构化变更：常见画像使用受控 `fact_key`，模型只在用户明确表达时输出 `upsert/delete/add/remove`。单值属性（如颜色、价格区间）更新时，旧事实标记为 `superseded`；集合属性（如品牌、关注品类）按元素增删；用户明确要求忘记时标记为 `deleted`。

旧版本仍保留用于审计，但 Prompt 和 `recall_user_memory` 只读取 `active` 事实。每次变更还保存 `fact_id`、置信度、来源会话和 `supersedes_id`，因此“喜欢红色 → 现在喜欢蓝色”不会把两条矛盾偏好同时注入模型。版本链与摘要并非无限增长：superseded/deleted 版本按更新时间保留 90 天（可配置）后由统一修剪函数物理删除，交互摘要只保留最近 20 条，`active` 事实永不修剪；文件与外置存储的两条写路径走同一套修剪规则

有效期与冲突优先级：`issue/behavior` 类事实按创建时间受 365 天有效期约束，超期不再注入；身份与偏好类豁免有效期（一年前的偏好仍然成立）。冲突优先级（2026-09 二次重构后）：同一单值键的新值经 `upsert` 让旧值 `superseded`，注入只看 `active`——同一时刻同键只有一条生效；调用方若持有更权威的实时值（如刚落库的会话内信息），可经 `exclude_keys` 显式排除 LTM 旧值（原"会话内 STM 优先"由该通用能力承接）。

文件、Redis 和 MySQL 存储均兼容旧版事实；旧记录读取时生成稳定 legacy 标识，后续变更时再渐进迁移到规范属性键。多实例写入分别通过进程内锁、Redis WATCH/MULTI 和 MySQL 用户级锁串行化，避免并发会话互相覆盖。

这套版本链还有一个隐藏福利：**时态查询**（2026-09 重构补齐语义）。事实的 `created_at` 即生效时刻，superseded/deleted 版本的 `updated_at` 即失效时刻——不需要新增任何字段，就能回答"3 月 1 日那天系统认为用户喜欢什么"（`facts_active_at(ts)`）。这和 Graphiti 这类图谱记忆框架的"双时态"模型是同构的：失效而非删除，历史可回放，审计可溯源。



## 相关性召回：从纯词面到混合检索（2026-09 重构）

之前 LTM 注入的相关性判断是纯词面匹配（汉字 bigram 的 Dice 系数），有一个很实在的短板：用户说"退货钱怎么打给我"，和记忆里的"偏好退款原路退回"在字面上一个词都不重叠，就召不回来——同义改述必漏。

重构后改成**语义 + 词面双路融合**：

```
score = 0.4 × dice(query, fact) + 0.6 × cosine(query向量, fact向量) + 类别权重 + 0.1 × exp(-age/180)
```

几个关键工程决策：

- **不引入向量数据库**。单用户活跃事实就几十条，应用侧暴力余弦完全够；嵌入向量存在独立的派生表/sidecar 文件里（`memory_fact_embeddings`），是 content 的函数，丢了重算就行，不污染记忆正本和审计链；
- **嵌入是写侧生成、读侧复用**。异步 memory job 巩固事实时顺手算好向量（内容寻址缓存：内容没变就不重复计费）；热路径每轮最多只算一次 query 的嵌入，失败、超时、没配置都**自动降级回纯词面**——语义是增强，不是依赖；
- **门槛只放宽不收紧**。词面达标的照旧注入（行为与之前逐字节一致）；词面不达标但融合相关性过阈值（默认 0.25）的才被语义路捞进来。开关 `memory_semantic_enabled` 默认关，灰度一键回滚；
- **漏注可观测**。注入候选数、过滤原因（TTL/阈值/键冲突）、选中明细全部进指标；Agent 主动 `recall_user_memory` 召回而自动注入没命中的，单独计数——漏注率第一次有了直接度量，而不是靠体感。

另外加了一个**巩固清理 sweep**（默认关闭）：扫描 legacy 键和余弦 >0.92 的语义重复簇，让 LLM 产出规范键 + 合并建议，但落库必须走和正常写入完全相同的校验与版本链协议——宁可少合并，不做旁路直写。合并错了也能从 90 天版本链里人工恢复。



## 记忆里的 PII 怎么处理

记忆系统对隐私数据的口径是"统一脱敏 + 业务例外"。手机号这类直接标识符在入库前统一替换成占位符，不管它出现在事实内容还是用户原话证据里；提取时用原文做证据校验，落库的却是脱敏版本，审计链路依然可验证

姓名和收货地址是例外，它们被有意保留。客服场景里"王小明的订单寄到张江路"这类记忆是业务必需的，没有它们记忆就失去价值。保留的前提是存储层的访问控制：记忆文件目录和数据库账号都有独立的权限边界，不会进入日志、导出通道或第三方系统

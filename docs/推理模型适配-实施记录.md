## 1. 未完成的门禁：T0 探针未实证（最高优先级）

计划的前置门禁是「目标模型必须支持 function calling（T0 探针实证）」。**本次实施
环境没有 `OPENAI_API_KEY`／`.env`，探针脚本未对任何真实端点运行过**，因此：

- 门禁结论**未知**（不是通过，也不是失败）。计划中「不支持则整个计划终止」的判定
  尚未发生；
- 内置画像（`model_profile.REGISTRY`）是按厂商文档写的**基线**，不是实测值——
  `supports_forced_tool_choice`、`reasoning_return_policy`、`temperature_mode`
  三项尤其需要探针确认（三家厂商在这三点上两两矛盾）；
- 代码侧的安全网是「未命中画像 = 现状行为逐字节不变」，因此本批代码合入**不改动
  现有部署的请求体**（默认 `model_name=gpt-4o-mini`、`DeepSeek-V4-Flash-*` 均未命中
  画像）。风险不在合入，而在**切换 `model_name` 之前**。

**切换前的必做动作**（顺序不可颠倒）：

```bash
# 1) 探针（输出画像 + 门禁判定 + 延迟/reasoning token 实测）
python -m app.scripts.probe_model_capability --model <目标模型> \
    --out app/sessions/model_profile.json

# 2) 门禁失败（退出码 2）→ 停止切换，回到选项一/二（探针脚本保留复用）
# 3) 门禁通过 → 把画像灌进部署配置（免发版）
python -m app.scripts.probe_model_capability --model <目标模型> --emit-overrides
#    → 填到 MODEL_PROFILE_OVERRIDES

# 4) 配置 EXTRACTION_MODEL 为非推理廉价模型（T1 部署动作）
# 5) 按 §2 用实测 P50/P95 与 reasoning token 校准 T2/T7/T8 的数值
```

`--dry-run` 可离线验证脚本接线（本仓库已用它跑通全流程，见 §7 测试）。

### 1.1 厂商差异速查（内置画像的依据，均需探针实证）

| 维度 | DeepSeek-reasoner | OpenAI o 系列 | Claude extended thinking |
|---|---|---|---|
| temperature | 接受但忽略 | 不支持（仅默认 1，传值 400） | thinking 开启时必须 =1 |
| function calling | 支持（与 reasoning 组合的约束需验证） | 支持 | 支持 |
| forced `tool_choice` | 需验证 | 需验证 | 需验证（与 thinking 组合另有约束） |
| reasoning 字段 | `reasoning_content`，**明确禁止回传** | 不返回原文（厂商内部管理） | thinking block **必须带 signature 原样回传** |
| 推理 token 计费 | 计入 output | 计入 `max_completion_tokens` | 计入 output，有 `budget_tokens` 上限 |

三者两两矛盾，正是不能按通用假设写代码、必须按画像分支的原因。内置 registry 的取值
即来自本表，**未经探针证实前只当基线**：`supports_forced_tool_choice`、
`reasoning_return_policy`、`temperature_mode` 三项最可能被实测推翻。

## 2. 待 T0 实测校准的定参（当前值为**临时**取值）

| 项 | 旧值 | 现值 | 依据 / 校准方式 |
|---|---|---|---|
| `llm_max_tokens` | 2048 | **8192** | 思考 token 与可见输出共享上限；按实测 reasoning token 峰值调整 |
| `context_window_tokens` | 32768 | **65536** | 不变式：输出预留（20%）≥ 输出上限；32768×20%≈6.5k < 8192 会失衡 |
| `llm_timeout_seconds` | 60 | **120** | 推理模型单调用常超 60s；按实测 **P95** 上调（预估 120–180） |
| `turn_budget_seconds` | 120 | **300** | `max_react_steps(8) × 单调用延迟` 会撞旧值；按实测二选一（降步数或抬预算），本次选抬预算（保复杂退款流程的步数余量） |
| `_MODEL_PRICES` 推理条目 | — | 待对账 | 现有推理单价是占位常量，**必须与账单对账**（验收 <5%）后才可对外引用 |

`max_react_steps` 保持 8：与 300s 预算组合后最坏墙钟 8×120s 由预算熔断兜底（不是
无界级数）。若实测 P95 > 37s，应改走「步数 8→6」以免预算被单步吃光。

## 3. 遗留风险（未在本期解决）

1. **多 Agent 无结构化终答协议**（计划已登记）：`multi_agent/agents.py` 的循环是
   旧语义——纯文本即终答、步数耗尽的收尾不挂工具。它比单 Agent 更兼容推理模型，
   但没有 `final_response` 协议保护。对齐协议是独立决策，**未在本期实施**。
2. **多 Agent 的 reasoning 不进审计**：T3 的双通道只接在 `react_runner`（单 Agent）。
   `SubAgent.handle` 的 assistant 消息仍直接进 `raw_messages`/审计，未做窗口/审计
   分离。多 Agent 部署若要"推理可审计"，需按 T3 同样改造该循环。
3. **多 Agent 未接 SSE reasoning**：`SubAgent` 没有 `emit_status`/`event_callback`
   通道（只有日志），T6 的透出目前仅单 Agent 生效。
4. **`gpt-5` 系未进 registry**：画像里的 o 系列是 o1/o3/o4；gpt-5 系的
   `max_completion_tokens`/`reasoning_effort` 组合未经探针，未登记（宁缺勿错——
   错登记会把非推理部署的请求体改坏）。需要时用 `MODEL_PROFILE_OVERRIDES` 显式加。
5. **Claude 的 `thinking` 预算注入是嵌套形态特例**：`reasoning_budget_param="thinking"`
   会注入 `{"type":"enabled","budget_tokens":N}`。若目标网关用的是扁平参数名，
   需在覆写里改（或扩展 `apply_profile`）。
6. **`online_quality` 的 lite judge 默认仍用被测模型**（`settings.model_name`）——
   与 eval-v2「judge ≠ 被测模型」的冻结协议不一致。本期只加了画像守卫并补了
   `--judge-model` 开关（默认行为不变），是否改为强制不同模型属独立决策。
7. **`rate_limit_daily_tokens` 未重估**：推理 token 全额计入日预算且量级不可预估，
   灰度期需按 T0 实测消耗重估（3–10×），并保证有用户级日预算兜底。

## 4. 关键实现决策（与计划的偏差点）

- **参数改写只在一处**：`llm/client.py::_wrap` 调用 `apply_profile`；17+ 个
  `chat.completions.create` 调用点零改动。计划里 T2 说的"调用点改为传意图而非值"
  落地为**注释声明语义**（`react_runner` 两处注明 temperature/max_tokens 是调用方
  偏好、是否发给厂商由画像层决定），而非改参数——否则改写面又摊回调用点。
- **降级链按备用模型画像重写**（计划未提，实现中发现）：`_wrap` 保留调用方原参
  快照，降级时从快照按 fallback 模型重写。否则 o 系列改名后的
  `max_completion_tokens` 会带给 gpt-4o 备用模型 → 400。
- **`estimate_llm_tokens` 改为键无关**（计划未提，实现中发现）：画像把
  `max_tokens` 改名后，原实现只按 `max_tokens` 取值 → 预留只算输入、输出上限被
  系统性漏算。公式未改，只让取值兼容两个键。
- **`ContextBuilder.fold_history` 修结构化 content 被 `str()` 的缺陷**（测试暴露）：
  原实现对 assistant 消息无条件 `str(content)`，会把 thinking 块列表变成 Python
  repr——既丢 signature（厂商 400），也让 required_signed 画像的窗口回传断链。
  现仅在 content 为字符串时折叠，结构化内容原样透传。
- **审计捕获与画像解耦**：捕获 reasoning 不依赖画像（未登记的推理模型照样可审计），
  只有"回传窗口"严格按画像放行（默认剥离）。这样画像漏配不会泄漏推理进请求体，
  也不会丢掉审计。
- **`sse_reasoning_enabled` 默认关**：`emit_reasoning` 关闭时是纯 no-op，
  因此"不透出模型原始思考"的既有断言继续成立；开启时先过输出 guardrails 并截断
  到 4000 字符（SSE_MAX_CHARS）。

## 6. 回滚

- **总回滚** = `MODEL_NAME` 改回旧模型：旧模型名未命中画像 → `apply_profile` 空操作，
  代码零改动即回到现状请求体；
- **独立开关**：`SSE_REASONING_ENABLED`（透出）、`EXTRACTION_MODEL`（辅助摘离）、
  `MODEL_PROFILE_OVERRIDES`（画像覆写，置空即回内置 registry）；
- **数据兼容**：`reasoning` 是消息上的 additive 字段（`full_turn_messages` → SQL 正本
  的 `content` JSON 整体落库、`_parse_msg` 整体读回），旧读取路径忽略未知字段即不受影响；
  `normalize_model_history` 只取 user + 最后一条非 tool-call assistant，中间带
  reasoning 的消息不进模型历史；
- **评测**：manifest 指纹新增 `model_profile`/`model.judge_profile`/原因子，
  旧 manifest 因 config_hash 变化会被 `verify_manifest_unchanged` 拒绝续跑——
  这是**预期**（基线不可比），新 run-id 重跑出新基线。

## 0. 结论摘要

1. **`effective_date` 当前是「三重语义共用一个字段」**：根目录/uploads 文档 = 审核发布基准日（`migrate_kb_metadata.py:71` 默认 2026-09-12；`upload_service.py:659` = 上传当日）；`evolved/` 文档 = **发布日 + 180 天的有效期上限**（`publisher.py:74` + `settings.py:353`）；商品库文档 = 常量 `2024-06-01`（`product_kb.py:41`，物理隔离命名空间，见 §1.1）。
2. **拆分推荐方案 A（evolved 增独立字段 `valid_until`）**：`effective_date` 回归「生效/发布日」单义，`valid_until` 承载「有效期上限」。理由：字段级语义单一、加字段向后兼容（`numpy_backend.py:83-85` 的 `Chunk(**c)` 有默认值即可）、不触碰构建期排除逻辑；方案 B（`status` 细分）把「日期语义」编码进「生命周期状态」，会同时改到构建期入选判定（`governance.py:151-159`）与词表隔离（`build_query_lexicon.py:314`），爆炸半径更大。
3. **aging 口径**：`app/review/scan.py:37-73` 把 `effective_date` 当作「基准日」，超期判定 = `effective_date < today - knowledge_aging_days(365)`。对 evolved 文档这等于给了 **180 天宽限**（基准日 = 发布日+180），且 `evolve_pending_aging_days(30)` 管的是另一件事（pending 候选未审核，`ledger.py:237-244`），两者不冲突但语义易混。拆分后 aging 应统一锚定「生效/发布日」，`valid_until` 另作时效上限供未来消费。
4. **`external_reference` 放开入索引 + 平台权威优先：本卡建议「暂不放开，先做元数据修正与语料版本化」**。现状是**没有任何文档以 `external_reference` 标记**，但**10 篇 F 类平台外机构条款以 `authority: platform` 身份就在索引里**（`check_corpus_v3.py:38-48`、`build_query_lexicon.py:62-73`），它们正是 v3 负例拒绝率低的主因（`简历指标来源.md:228-229`）。放开 = 改负例压力的构成，属**评测口径变更**，必须与 v3.5 语料轮同批冻结（显式风险见 §4.4）。
5. **前置阻塞（必须先解决，否则 A/B 无法归因）**：`docs/RAG切分与文档处理优化方案.md` §B.4 第 1 条自述「959 例检索评测 A/B 门禁未执行」；且本次取证发现 **2026-09-10 门禁轮的索引含 `archive/` 文档**（`artifacts/eval/v3/gate/dev-final/report.json` 的 `hit_keys` 里出现 `archive/旧版价保规则存档.md`），而 `archive/` 构建期排除是 2026-09-12 才落地的（`governance.py:24` + `parsers.py:1051-1052`、`:1076-1079`）、分块/指纹变更在 2026-09-15（`fingerprint.py:18`）。**结论：简历引用的 66.9% / 21.4% 等门禁数字是旧语料旧索引口径，不能直接当作现行基线**（待验证：需在新索引上重跑 dev 959）。

## 2. 拆分方案：生效日 vs 有效期上限

### 2.1 方案 A：`evolved/` 增加独立字段（推荐）

**语义重定义**

- `effective_date` = **生效/发布日**（evolved：`publisher._wrap_frontmatter` 里的 `now`，即 `last_validated` 同日；根/uploads：维持现有基准日语义）。
- 新增 `valid_until` = **有效期上限**（evolved：发布日 + `evolve_effective_days`；根/uploads：可选，缺省空 = 不过期）。

**改动面**

| 层 | 位置 | 改动 |
| --- | --- | --- |
| frontmatter 生产 | `publisher.py:74`/`:87`/`:100` | `effective_date=now`，新增 `valid_until=now+180d`；人工支路（`:76-91`）与自动支路（`:92-104`）同改 |
| 校验器 | `governance.py:125-148` | 新增可选字段格式校验（`_valid_date` 复用）；是否强制 evolved 必填需决策（建议可选，缺省=无上限） |
| Chunk 透传 | `chunker.py:87-91`（字段）、`:172-178`（读 meta）、`:255-257`（赋值）、`:791-799`（`_make_chunk` 签名） | 加 `valid_until: str = ""`，与现有三字段同路径 |
| 三后端 | `es_backend.py:105-107`（mapping）/`:155-157`（doc）、`chroma_backend.py:99-101`/`:144`/`:216`、`numpy_backend.py:48-56`（`to_dict` 自动覆盖）+ `:83-85`（`Chunk(**c)` 旧索引兼容） | ES 需**新建索引**（mapping 在 upsert 时创建，`es_backend.py:135-146`）；chroma metadata 加键；numpy 旧索引可读但缺字段 |
| aging 消费 | `scan.py:37-73` | 若采用 §3.3 的统一口径，锚点改为 `effective_date`（对 evolved 即发布日）→ 两篇 evolved 的超期日从 2028-02-28/2028-03-07 **提前到** 2027-09-01/2027-09-08（行为变化，但仅影响 ops 页面，不进检索） |
| 指纹 | `fingerprint.py:14-18` | **必须 bump `PARSER_CHUNKER_VERSION`**：chunker 输出新增字段 = 索引内容变化；不 bump 则旧索引静默缺 `valid_until`（该文件注释明确「改动解析器或分块器输出时必须 bump」） |
| 迁移 | 2 篇 evolved 文档 frontmatter 改写（`effective_date` 回填为发布日、加 `valid_until`）；135 篇根文档不动（可后续补 `valid_until` 空值或省略） | 迁移脚本可仿 `migrate_kb_metadata.py` 的「只补缺失项」模式；改动**不触碰正文**，embedding 不变（frontmatter 不进 chunk 正文，`chunker.py:172-177` 先 `parse_frontmatter` 再切 body） |

**对既有指纹与索引重建的影响**：需重建一次（新增字段 + evolved 的 `effective_date` 值变化）。因为 frontmatter 不参与正文/embedding，重建后 `recall/MRR/nDCG` 预期逐例不变（**待验证**：必须用 per-case `hit_keys` diff 断言，见 §5.1 Arm 1）。

### 2.2 方案 B：`status` 细分 + 保留单字段语义

思路：保持只有一个日期字段，用 `status` 的取值区分「这个日期是生效日还是有效期上限」，例如 `active`（日期=生效日）/ `evolved_active`（日期=有效期上限）/ `archived` / `expired`。

**改动面**

| 层 | 位置 | 改动 |
| --- | --- | --- |
| 枚举 | `governance.py:25` `_VALID_STATUS` | 扩枚举；同步 `:134-135` 校验分支 |
| 入选判定 | `governance.py:151-159` | 每个新状态都要定义是否入索引（`archived` 语义会与新状态交叉） |
| 词表隔离 | `build_query_lexicon.py:314`（`status == "archived"`） | 新状态需同步，否则隔离失效 |
| 构建期 | `parsers.py:1079` | 无需改代码，但语义分支靠 `is_index_eligible` |
| Chunk/后端 | 无字段变化（`status` 已透传） | **零后端改动**——这是 B 唯一的优势 |
| 指纹 | 同上需 bump（frontmatter 值变化 → 索引元数据变化） | 需重建 |
| 迁移 | 2 篇 evolved 改 `status`；但 133 篇根文档的「日期语义」仍无法自解释（它们的 `effective_date` 是审核基准日，不是生效日） | 语义仍靠约定 |

**致命问题**：B 没有解决「一个文档同时需要生效日与有效期上限」的需求——未来做时效过滤时，evolved 文档既要知道「何时开始有效」也要知道「何时失效」，单字段 + 状态位表达不了（除非再塞第三个状态值，退化成 A 的劣化版）。且 `status` 是生命周期状态，把日期语义混进去后，`archived`（下架）与「已过期」（时效）会互相纠缠。

### 2.3 对比与推荐

| 维度 | A：独立字段 | B：status 细分 |
| --- | --- | --- |
| 字段语义 | 一字段一义 | 一字段两义（由状态位选择） |
| 后端改动 | 三后端加键 + ES 新索引 | 无 |
| 构建期入选逻辑风险 | 无 | 高（改 `is_index_eligible`，可能把文档移出索引 → 直接改评测口径） |
| 迁移成本 | 2 篇 evolved frontmatter + 一次重建 | 2 篇 frontmatter + 一次重建 |
| 未来时效过滤可用性 | 可直接用两个日期表达区间 | 表达不了区间 |
| 死字段风险 | 新增字段若无消费方 → 与现有三字段同罪（B.3 已声明「长期无人消费即删」） | 不新增字段，但状态值同样可能无人消费 |

**推荐 A**，并附一条硬性前置：**A 落地时必须同时指定 `valid_until` 的消费方**（建议 `scan.py` 的 aging 输出增加「有效期上限」列 + `revalidate` 排序改读 `valid_until` 优先），否则就是再造一个死字段——按 `docs/RAG切分与文档处理优化方案.md:270` 的口径，无消费方即应删除。

## 3. 与 `app/review/scan.py` 的 aging 口径对齐

### 3.1 现状算法

```
app/review/scan.py:46-47   threshold = date.today(); cutoff = threshold - timedelta(days=aging_days)
app/review/scan.py:55-72   effective_date 缺失 → unknown；effective < cutoff → expired；否则 valid
```

- `aging_days` 注入自 `settings.knowledge_aging_days = 365`（`settings.py:284-286`），调用点 `webapp.py:418-419`。
- `evolve_pending_aging_days = 30`（`settings.py:350`）**不是同一个东西**：它作用于 `ledger.list_pending`（`ledger.py:237-244`，按 pending 候选的 `created` 时间判「超过 30 天未审核」），消费点 `run_evolution.py:445/654/786`、`webapp.py:73`。两者共用「aging」这个词但对象不同（已发布文档 vs 待审候选），不冲突，但**文档与 UI 上应避免混称**。
- 实现与 docstring 不符（小问题）：`scan.py:3-5` 的模块 docstring 说「收集 effective_date 早于阈值（或缺失）的文档」，但实现**把所有文档都返回**（`scan.py:67-72` 也 append `valid`），`webapp.py:159-162` 的页面标题是「过期/临期知识文档（{n}）」，`n` 实为 `kb_dir` 下全部 145 篇 md（135 可索引 + 10 archive；本次实测计数）。运营看到的「145 条」是误读源。

### 3.2 对齐点

1. 两者都以 `effective_date` 为唯一日期锚（`scan.py:55`、`revalidate.py:97-107`），**语义拆分是共同前置**。
2. 拆分后建议统一口径：`expired ⇔ effective_date + knowledge_aging_days < today`，即「生效日起 365 天未复核 → 提示复核」；对 evolved 文档这比现状**提前 180 天**触发（现状：基准日=发布+180，故 545 天后才 expired）。
3. `valid_until` 与 aging 的关系建议：`valid_until` 是「有效期上限」（到点必须复核/重接地），aging 是「复核提醒」——两者可以不同（180 < 365），届时 ops 页面应分别展示「临期（接近 valid_until）」与「超期未复核（超过 aging）」。

### 3.3 冲突点（必须显式处理）

1. **日期锚冲突**：evolved 的 `effective_date` 是「发布+180」，而根文档是「审核发布日」。同一个 aging 阈值（365）作用在两种语义上，等于 evolved 文档比同批人工文档多 180 天免检窗口——这不是设计选择，是语义混用的副作用。
2. **`valid_until` 与检索消费的潜在打架（若将来做时效过滤）**：若按「`valid_until < today` 即排除」过滤，evolved 文档在第 181 天自动失效——与「自进化知识持续有效直到被替换」的现状不符（现状 `lifecycle.settle_replacement` 只在被新版本替换时下架，`lifecycle.py:85-115`）。**因此 `valid_until` 到期语义建议定义为「触发复核/重接地」而非「自动下架」**（与 `revalidate.py` 的 P1-2 机制天然衔接），否则会与替换式淘汰（`ledger`/`human_store` 的 superseded 链路）冲突。
3. **`unknown` 口径**：`scan.py:56-60` 把缺 `effective_date` 记为 unknown，但构建期 `validate_metadata` 对 md/txt 是**强制**要求该字段（`governance.py:140-143`，strict 构建失败）——即「可索引文档不会 unknown」。unknown 实际只会来自未走构建校验的目录，例如 `archive/` 的历史文档（本次实测：`archive/2024大促规则存档.md`、`archive/客服响应SLO旧标准.md` 均无 frontmatter → 在 aging 页显示为 unknown）。这层冗余可以保留（防御性），但不应作为运营信号解读。
4. **`archive/` 参与 aging 扫描**：`scan.py:50` 用 `kb_dir.rglob("*.md")`，不过滤 `governance.is_indexable`，因此 archive 的 10 篇历史文档也会进 aging 列表（无 frontmatter → 全部计 unknown，见上条）。这与「排除目录」的治理口径不一致，是运营噪音源（也解释了「unknown 应提示补全」的提示为何对归档文档无意义）。

## 4. `external_reference` 是否放开入索引 + 平台权威优先排序

### 4.1 先厘清三套「authority」，避免混谈

| 体系 | 位置 | 取值 | 判定依据 | 消费方 |
| --- | --- | --- | --- | --- |
| 治理元数据 `authority` | `governance.py:26`、`:138-139`、`:151-159` | `platform` / `external_reference` | 文档 frontmatter | 构建期入选（排除 external_reference）；词表隔离 |
| 自进化权威性 `authority_kind()` | `app/evolution/authority.py:27-49` | `authoritative` / `managed` | **路径 + frontmatter**（非 evolved/ 即 authoritative；evolved/ 一律 managed） | 人工知识去重/发布（`human_evaluator.py:461`、`human_publish.py:576`） |
| 商品命名空间 `authority` | `product_kb.py:38`、`:166-171` | `product` | 商品文档目录 + 平铺 md 断言 | 商品索引装载（fail-closed） |

**注意**：`authority_kind()` 与 frontmatter 的 `authority` 字段**无关**（`authority.py:3-4` 明确「只依据位置 + frontmatter 两个事实判定，owner 字段彻底不参与」，但同样也不读 `authority` 字段）。P1-5 说的「平台权威优先排序」若按 `authority_kind()` 实现，会得到「根目录 > evolved/」的排序，而不是「platform > external_reference」；**这是两件事，必须先定义清楚要哪一个**。另外 `product` 是治理校验器不认识的值（`governance.py:26` 的白名单只有两个），说明治理校验器与商品命名空间是两套独立体系，扩枚举时要防止把商品文档卷进政策库校验（当前靠 `ALLOWED_ROOTS` 物理隔离，`governance.py:22`）。

### 4.2 当前为何在构建期排除

- `is_index_eligible` 对 `authority=external_reference` 返回 False（`governance.py:157-158`），`parsers.py:1079` 据此跳过；
- `validate_metadata` 直接禁止 `active + external_reference`（`governance.py:144-145`）——即**当前不存在合法路径**让 external_reference 文档以 active 身份进入索引；
- 设计意图（模块 docstring，`governance.py:10`）：「`archived` 或 `external_reference` 一律**不进线上回答索引**」——外部机构条款不能作为平台规则回答用户。

### 4.3 放开后的收益

1. **覆盖面**：若未来接入银行/快递/航司/延保等外部条款，可用于「非平台责任」的解释性回答（例如「快递公司赔偿标准由承运方制定，平台协助索赔」）。当前这 10 篇 F 类文档已以 `platform` 身份在库，所以**收益不是「新增可检索内容」，而是「把已在库的内容标注正确、并在排序上区分」**——这直接改变回答姿态（现在它们与平台规则同权，可能被当作平台承诺）。
2. **可运维性**：ES 侧已可按 `authority` 过滤（`es_backend.py:107` mapping 为 keyword），放开后运营可直接查「哪些回答引用了外部条款」。
3. **负例压力的可控化**：若平台优先排序能把 F 类文档挤出 Top-K，理论上负例拒绝率会上升——但这是**评测口径变更**，不是免费的指标改善（见下）。

### 4.4 风险（含显式标注的评测口径污染）

> **【评测口径污染风险 · 显式标注】** v3 负例拒绝门禁（`≥90%`）是简历指标来源（`简历指标来源.md:224-235`、`语料补足与评测v3计划.md:70`）。F 类 10 篇文档当前以 `platform` 身份参与检索，是负例失分主因（`简历指标来源.md:228-229`：银行/快递/航司/延保被 0.99+ 命中）。**任何改变这 10 篇入选/排序的改动，都会改变 959 条冻结集的语义**（负例更易拒绝 ≠ 模型变强）。因此：
> - 不允许把「F 类 relabel + 降权」的结果直接与 `66.9%` 对比并宣称提升；
> - 必须走 v3.5 语料轮重新冻结（`语料补足与评测v3计划.md:41`、`:85`、`:268`），或明确标注为「新口径，与旧数字不可比」。

其余风险：

1. **权威性**：`external_reference` 入索引后必须保证回答侧不把它当平台规则——当前回答侧没有「按权威性改写措辞」的机制（`authority` 不进打分、不进 prompt），放开后需要额外的回答约束，否则等于把「外规当平台规则」的错误从检索层挪到生成层。
2. **打分实现的硬约束**：本机 `.env:59`/`:166` 为 `RAG_RERANK=none`，阈值被注释掉（`.env:190-194` 自述「hybrid+rerank=none 的 RRF 分无语义，配了会被 /readyz 判为 rag unavailable」，与 `health.py:187-201` 一致）。**在 RRF 分上做乘子式降权没有意义**（分数量纲是秩融合分，`retriever_factory.py:245-247` 也明确「RRF 分不得参与阈值判断」）。平台优先若要实现，只有两条路：(a) 启用 reranker 后在 rerank 分上做（需重新校准阈值）；(b) 在 `final_search` 的**折叠/截断之前做秩级重排**（不碰分数）——(b) 不依赖分数语义，但会改变 Top-K 构成，仍须 A/B。
3. **负例压力转移**：把 F 类降权/移出后，负例的「近域诱惑」可能转移到其余平台文档（D 类数值易混文档），负例拒绝率的提升可能小于预期——**待验证**（需 A/B 实测）。
4. **索引与评测的旧口径残留**：见 §0.5 的发现（2026-09-10 门禁轮索引含 archive），任何 A/B 必须显式冻结语料与索引，否则数字不可归因。

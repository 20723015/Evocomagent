# P3-1 回复流式改造 —— 评估卡（结论：倾向 A，且先证明收益；守卫优先）

- **日期**：2026-09-18
- **依据**：本仓库代码取证（所有论断附 `文件:行号`；无法取证处显式标注「待验证」）
- **对应计划**：《能力补全全量计划.md》P3-1（第 243–252 行）
- **本卡边界**：只出评估结论与可实测判据。**不实施**：不改 SSE 端点、不改 `chat.js`、不改 `final_response`/守卫链、不新增 settings 开关。

## 0. 结论摘要

1. **现状确认**：SSE 只流过程事件（`meta`/`thought`/`tool_call`/`tool_result`/可选 `reasoning`），最终回复在整轮 Agent 任务结束后由处理器**一次性**发出（`app/server/main.py:1279`、`:1290-1316`）。前端 `chat.js` 收到 `reply` 事件后整块渲染（`app/server/static/js/chat.js:493`、`:321-330`）。
2. **不能照抄逐 token 流式的根因（代码证据链）**：回复文本产生于 `final_response` 工具调用的参数里，**与非流式的 LLM 调用同批返回**（`app/agent/react_runner.py:166-172` 未开 `stream=True`；`app/agent/final_response.py:25-59`）；此后还要经过 `fact_guard` 的**按句删除**（`app/agent/fact_guard.py:156-179`）、`final_reply_guard` 的**整段替换**（`app/agent/write_ops.py:221-233`）、输出安全/PII 的**整段替换与脱敏**（`app/agent/turn_finalizer.py:237-258`），以及 SSE 层的**第二次** `check_output`（`app/server/main.py:1296-1300`）。真流式 = 把这些守卫之前（或之中）的文本先给用户看，再撤回/改写已流出的话术。
3. **方案 A（伪流式）的落点只有一处低风险选择**：`main.py:1293-1300` 之后（`task.result()` + SSE 侧守卫之后）、`reply` 事件之前，按句切分并追加 `reply_delta` 事件；守卫全保留、最终 `reply` 事件仍是权威全量（老客户端忽略未知事件即可）。**A 不能降低首句到达时间**——首句与现状的 `reply` 同刻到达（因为生成与守卫都在此之前完成），它的收益是「过程事件 → 回复」的连续感（感知/产品体验），不是延迟指标。
4. **可实测判据（不实施，只设计）**：在 SSE 路径补 `t_first_content`（请求开始 → 首个回复内容字节）与 `t_full_text` 两个时间戳（当前 SSE 路径**没有任何**延迟埋点：`record_chat_latency` 只在非流式端点，`main.py:296-297`），用固定用例集跑 A/B：若 `t_first_content` 的 Δ ≈ 0（阈值建议 |Δ| < 50ms）且产品不接受「打字感」这一纯体验收益，则**留档不做**。若要做 A2 变体（守卫后、`commit_turn` 前流出，见 §3.2），必须先补 `StageTimings.persist_ms` 埋点——该字段目前**从未被赋值**（`app/agent/turn_context.py:49`、`:56`；全仓只有 `react_ms` 与 `context_build_ms` 被写）。
5. **守卫优先级高于流式**：任何流式改动必须满足不变式「流出的文本拼接 == 最终 `result.reply`，且不早于守卫执行」；这条不变式应作为实施时的硬测试（§5.4）。方案 B（拆 `final_response` 协议、事实先流/承诺后流）**不推荐**：它要么让承诺类内容绕过守卫，要么让协议复杂度翻倍，且本项目已有更省事的延迟杠杆（P3-2 的步数/预算校准）。

## 1. 现状取证

### 1.1 SSE 现在流什么

事件序列（`main.py:1083-1112` docstring，与实现一致）：

```
meta → thought* → tool_call* / tool_result* → reply → handoff? → end
（可选：sse_reasoning_enabled=true 时 thought 前有 reasoning*；GET 版首帧 deprecation）
```

- 帧格式：`event: <type>\ndata: <json>\n\n`（`main.py:101-103`）。
- 过程事件的产生：ReAct 每步 `agent.emit_status(...)`（`app/agent/react_runner.py:136-143`）→ `chat.emit_status` → `_emit_event("thought", …)`（`app/agent/chat.py:461-464`、`:641-643`）；工具调用/结果由 `ToolTurnState(event_callback=…)` 同路发出（`chat.py:287-291`）。
- 事件进 SSE 的通道：处理器把 `agent.event_callback` 绑到 `loop.call_soon_threadsafe(queue.put_nowait, …)`（`main.py:1276-1278`），生成器循环 `yield _sse(etype, data)`（`main.py:1290-1292`）。
- **最终回复**：`result = task.result()`（`:1293`）→ SSE 层第二次 `check_output`（`:1295-1300`）→ `yield _sse("reply", {reply, intent, confidence, requires_human, follow_up_question})`（`:1302-1316`）→ `handoff` 事件（`:1317-1321`）→ `agent.close()`（`:1323-1330`）→ `end`。
- 因此「最终回复一整块吐出」是**结构性的**：`run_agent_turn` 把整个 `agent.chat()` 丢进线程池（`app/server/runtime.py:55-67`），`chat()` 内部走完 ReAct + 收尾管线才返回（`app/agent/chat.py:267-284`、`:400-402`）。

### 1.2 前端如何消费

- `chat.js:387-430` `streamChat()` 逐帧解析 SSE，`onEvent` 分发。
- `chat.js:493`：`if (type === "reply") { replyData = data; finalizeBotTurn(dom, data); return; }`——**整块**渲染。
- `chat.js:321-330` `finalizeBotTurn`：`dom.bubble.innerHTML = renderMd(r.reply)` 一次性替换气泡内容，并加元信息 chips。
- 渲染器是轻量增量安全的：`common.js:15-20` `renderMd` = 转义 HTML → `` `code` `` → `**bold**` → 换行，无块级 Markdown（无代码围栏/表格/列表解析），因此「累加文本后重渲染」在 A 方案里成本极低（风险见 §3.5）。
- 过程事件另存 `traceLog`（`chat.js:477-490`、`:535-543`），刷新后由 `renderTranscript` 还原（`:342-365`）——A 方案若把回复切成多条事件，转写缓存仍只存最终 `reply`（`:501-503`），无需改存储。

### 1.3 埋点现状（与 P3-2 相关的缺口）

| 指标/字段 | 位置 | 现状 |
| --- | --- | --- |
| `chat_latency_seconds` | `app/observability/metrics.py:21-24`、`:266-267` | **只在非流式 `POST /v1/chat` 记录**（`main.py:296-297`）；SSE 路径无记录 |
| `StageTimings.context_build_ms` | `turn_context.py:46` | 有赋值（`react_runner.py:158` 累加） |
| `StageTimings.react_ms` | `turn_context.py:47` | 有赋值（`chat.py:385`，实际是「ReAct 结束时的总耗时」） |
| `StageTimings.finalize_ms` / `persist_ms` | `turn_context.py:48-49`、`:55-56` | **全仓无任何赋值**（grep 仅命中声明与序列化）→ 恒为 0.0，无法区分「守卫耗时」与「落库耗时」 |
| 轮次 usage（含 timings/latency_ms） | `turn_context.py:150-157` → `turn_repository.py:145-171` | 已随 turn archive 落盘（`recorder.record(..., usage=ctx.to_usage_dict())`），可作为离线分析的取数口 |

## 2. 为什么不能照抄逐 token 流式：守卫链的代码证据

### 2.1 生成与终止在同一个结构化调用里

- 终止协议：模型必须调用 `final_response(intent, reply, requires_human, follow_up_question)`，参数经 Pydantic 严格校验，校验失败回结构化纠错（`app/agent/final_response.py:25-59`、`:73-121`）。
- 调用点：`react_runner.py:166-172` 用 `agent.client.chat.completions.create(...)`——**没有 `stream=True`**；`reply` 是工具调用参数 JSON 里的一个字段（`:212-219` 取出并校验）。
- 含义：即使把 LLM 调用改成流式，流出来的也是**工具参数 JSON 的增量片段**（含转义、可能跨 chunk 截断），不是可直接展示的回复文本；要展示必须先组装 JSON 并等 `reply` 字段完整。也就是说「逐 token 流式」在本项目等于「边组装 JSON 边猜文本」——**先流出的是未完成 JSON，不是未守卫的回复**（这比「未守卫文本」更糟：会展示 JSON 片段）。

### 2.2 `fact_guard`：数字级按句删除

- 逐句抽取数字声明（金额/时效/比例/计数），要求每个数字在**本轮证据原文**中可找到，否则**删除整句**（`app/agent/fact_guard.py:19-23` 正则与分句、`:62-70` 句级判定、`:156-170` 删除逻辑）。
- 全部被删 → 整段替换为「需核实/转人工」话术（`fact_guard.py:171-174`）；有删除且残留 → 追加免责句（`:175-179`）。
- 触发条件决定了它**必须在生成之后**：证据集（工具结果 + 检索片段）只有在 ReAct 循环结束、所有工具返回后才完整（证据文本经 `ctx.evidence_texts` 进入收尾，`turn_finalizer.py:160-167`）。
- 后果：真流式下，模型先说的「7 天无理由、赔付 30 元」等数字可能随后被删——用户已经看到了无证据数字。

### 2.3 `final_reply_guard`：整段改写

- 无对应业务回执时，禁止越级宣称退款状态；命中即**整段替换**为 `_SAFE_REWRITE_REPLY`（`app/agent/write_ops.py:221-233`、`:78-82`），并把 `requires_human=True`、记 `refund_claim_without_evidence`（`turn_finalizer.py:141-150`）。
- 改写对象是**全文**（`return _SAFE_REWRITE_REPLY, True`），不是句子级——即已流出的任何一句「退款已完成」都无法局部修补，只能整段撤回。

### 2.4 输出安全与 PII：整段替换 + 脱敏

- `turn_finalizer.py:237-258`：`check_output(reply, user_emotion=…)` 命中 → 整段替换为 `SAFE_FALLBACK_REPLY`；随后 PII 脱敏 `sanitize_text` 可能改写正文（`:250-258`）。
- SSE 层**还有一次** `check_output(reply)`（`main.py:1295-1300`）——即处理器对最终回复保留最终否决权。任何在 `task.result()` 之前流出的文本都绕过了这道否决。

### 2.5 冲突链小结

| 守卫 | 粒度 | 位置（生成之后） | 真流式的后果 |
| --- | --- | --- | --- |
| `final_response` 协议 | 一次调用产出全文 | 生成时（`react_runner.py:212-219`） | 流出的只能是 JSON 增量，不可展示 |
| `fact_guard` | 句子删除 / 全删替换 | `turn_finalizer.py:160-167` | 已展示的无证据数字要撤回 |
| `final_reply_guard` | 整段替换 | `turn_finalizer.py:141-150` | 已展示的「已退款」要撤回 |
| 输出安全 + PII | 整段替换 / 脱敏 | `turn_finalizer.py:237-258` | 已展示的违规/隐私内容要撤回 |
| SSE 层 `check_output` | 整段替换 | `main.py:1295-1300` | 同上（最后一道闸） |
| 升级/情绪（P1-1） | 改 intent/requires_human | `turn_finalizer.py:209-235` | 回复文本相同但元信息不同 → 提前流出会让「转人工」状态迟到 |

**结论**：在本项目的守卫拓扑下，「逐 token 流式」不是工程问题而是**语义冲突**——守卫的输入必须是完整回复与完整证据，输出必须是用户最终看到的全文；这两条约束与「先流出、后校验」互斥。

## 3. 候选方案 A：伪流式（finalize 完成后按句流出）

### 3.1 落点 A1（推荐，零延迟收益、零守卫风险）

在 `_chat_stream_response` 内、`main.py:1293-1300` 之后（即 `result = task.result()` 且 SSE 层 `check_output` 通过之后），把 `reply` 按句切分并逐条 `yield _sse("reply_delta", {"text": …, "index": n, "done": bool})`，随后**保留**现有的 `reply` 事件作为权威全量。

- 切分实现：复用 `fact_guard._SENT_SPLIT_RE`（`fact_guard.py:23`，按 `。！？!?；;\n` 后切分）的等价规则；若不愿跨模块引用私有常量，实施时抽成公共工具（属实施细节，本卡不落代码）。
- 节奏：每句后 `await asyncio.sleep(pacing)`（建议常量 30–60ms，总追加时间上限 ≤1.2s；**不新增 settings 开关**，节奏常量写死在处理器里，若需可调应走单独审批）。
- 兼容性：老客户端按 SSE 规范忽略未知事件（先例：`reasoning` 事件，`main.py:1096-1104`）；`reply` 事件字段不变（`:1302-1316`）。
- 顺序：`reply_delta*` 在 `reply` 之前 → 现有断言 `events[-2] == "reply"`（`tests/unit/test_observability.py:203`）与 `data: ` 倒数第二行取 reply（`:207`）**继续成立**，测试改动面小。
- `handoff` 工单内容仍用最终 `reply`（`main.py:174` 的同步逻辑不变），无一致性风险。

### 3.2 落点 A2（不推荐，除非实测 persist 显著）

若要在 `TurnFinalizer.finalize` 内部、守卫（步骤 1–4）之后、`commit_turn`（步骤 6）之前流出（`turn_finalizer.py:54-71`），可提前 `persist_ms` 一段时间。代价与前提：

- **破坏「先落库后回话」纪律**：`commit_turn` 会清 `pending_turn`（`turn_repository.py:57-73`）；若流出后崩溃，用户已见回复而会话仍标记 pending（下次进入提示「上次回复未完成」）。
- **必须先补 `persist_ms` 埋点并实测**（当前恒 0，`turn_context.py:49`）。若 P95 < 100ms，收益可忽略，不值得承担顺序风险。
- 需要把事件回调从 SSE 处理器透到 finalizer（当前 `ctx`/finalizer 无 event_callback 直连；只有 `agent.emit_status` 一路，`chat.py:461-464`），改动面大于 A1。

### 3.3 前端消费（A1）

- `chat.js` 的 `onEvent` 增加分支：`reply_delta` → 累加 `pendingText` → `dom.bubble.innerHTML = renderMd(pendingText)`（`common.js:15-20` 的渲染器对部分文本安全）→ `scrollBottom()`；`reply` 事件到达时用全量覆盖（`finalizeBotTurn` 不变，`chat.js:321-330`）。
- 转写缓存只存最终 `reply`（`chat.js:501-503`），刷新还原路径（`:342-365`）无需改。
- 可选体验细节：`reply_delta` 期间隐藏 typing 占位（`chat.js:196-199`）。

### 3.4 改动面清单（若实施 A1）

| 文件 | 改动 | 备注 |
| --- | --- | --- |
| `app/server/main.py`（`_chat_stream_response`，`:1290-1320`） | 新增按句切分 + `reply_delta` 事件循环 | 唯一服务端改动点；不动 `runtime`/`agent` |
| `app/server/static/js/chat.js`（`onEvent`/`finalizeBotTurn`） | 累加渲染 | 纯前端；无构建链（`common.js:1` 自述） |
| `tests/unit/test_observability.py` | 可加一条「`reply_delta` 拼接 == `reply`」断言 | 现有 `events[-2] == "reply"` 不需改（§3.1） |
| 埋点 | 新增 `t_first_content`/`t_full_text`（建议进 `to_usage_dict` 或新直方图） | 见 §5.2 |
| settings | **无** | 不新增开关 |

### 3.5 风险

1. **Markdown 边界**：`renderMd` 只处理行内 `` ` `` 与 `**`；若 `**粗体**` 或 `` `code` `` 被句切分劈开，会出现瞬时渲染瑕疵，下一帧自愈。可接受（无块级语法）。
2. **总时长增加**：全量文本到达比现状晚 `pacing × 句数`（上限受控）。对「SLO 3 秒首响」（`app/agent/rag/knowledge/客服SOP与应答手册.md:14`、`:267`）无帮助——首句到达时间不变。
3. **客户端断连/刷新**：`reply_delta` 期间断连 → 现有断连移交逻辑不变（`main.py:1346-1365`），前端 `replyData` 为空 → 现有「连接中断,未收到回复」分支（`chat.js:511-513`）触发，行为与现状一致（用户看到的半截文本会被错误提示覆盖，**待验证**：需要实测确认，见 §5.2）。
4. **多消费者**：除 web 前端外，`app/server/channels.py`（webhook 渠道）与 MCP 侧不消费 SSE（渠道走 `run_agent_turn` 后整包出站，`channels.py:135-151`），A1 对它们零影响。
5. **`reply` 事件仍是权威**：如果未来某消费者只读 `reply_delta`，会拿到与 `reply` 可能不一致的拼接（只要实现保证同源即不会；该保证必须由测试锁定，§5.4）。

## 4. 候选方案 B：分段流式（不推荐）

计划描述：事实性结论先流、承诺性内容守卫后流，需拆 `final_response` 协议（`能力补全全量计划.md:249-250`）。

**为什么不推荐（代码依据）**：

1. 拆分协议意味着 `final_response` 要增加「事实段/承诺段」结构化字段，Pydantic 模型与纠错逻辑同步扩（`final_response.py:73-121`），并要改 system 指令与提示词（`:61-70`）——协议面扩大，模型遵从度与纠错率都是新风险（现有纯文本纠错已计指标 `record_final_protocol_correction`，`react_runner.py:188-191`）。
2. 「事实性结论先流」仍然要过 `fact_guard`（数字必须能在证据中找到），而事实段恰恰是数字最密集的部分——**先流事实 = 先流最需要守卫的文本**，与计划假设相反。
3. 「承诺性内容守卫后流」无法覆盖 `final_reply_guard` 的整段替换（`write_ops.py:231-232` 返回的是全文替换），除非协议层面把承诺段完全隔离——那又回到 1 的复杂度。
4. 收益上限有限：真正决定首句延迟的是 ReAct 步数与工具往返（`settings.py:29-33` 的 `max_react_steps=8` / `turn_budget_seconds=300` 未校准），B 只能省下 `finalize` 的一小段（且 `finalize_ms` 从未被测量，`turn_context.py:48`）。

**若仍要评估 B**，应先做「拆协议后模型是否还能稳定产出结构化终答」的可行性探针（离线 50–100 例，看协议纠错率），再谈流式——本卡不建议投入。

## 5. 结论与可实测判据

### 5.1 判据（首句延迟怎么测）

定义（服务端口径，避免把网络抖动混进来）：

- `t0` = SSE 生成器开始处理请求（`_stream()` 入口，`main.py:1225`；或用 `request_id` 建立时刻 `:1229`）。
- `t_first_content` = 写出**第一个回复内容字节**的时刻（A1 下 = 第一个 `reply_delta`；现状下 = `reply` 事件）。
- `t_full_text` = 写出最后一个回复内容字节的时刻（A1 下 = `reply` 事件；现状同）。
- 判读：**A1 的 `t_first_content` 与现状的差值 Δ 是核心判据**。理论上 Δ ≈ 0（两者都在 `task.result()` 之后），因此 A1 的价值只能用体验判据衡量（见下），不能用延迟判据。
- 若测 A2：Δ = `persist_ms` + `handoff/close` 中可提前的部分 → **只有实测 `persist_ms` P95 ≥ 100ms 才值得继续评估**。

### 5.3 判读阈值与留档条件

| 判据 | 阈值 | 不满足时的动作 |
| --- | --- | --- |
| `t_first_content` Δ（A1 vs 现状） | 期望 \|Δ\| < 50ms（同刻到达） | 若 Δ > 50ms 且无体验收益 → 回退 |
| `t_full_text` 增量 | ≤ 1.2s（pacing 预算） | 超出即调小 pacing 或不做 |
| `persist_ms` P95（决定 A2） | ≥ 100ms 才评估 A2 | < 100ms → A2 不做 |
| 拼接一致性 | `"".join(deltas) == reply` 100% | 任一例不一致 → 不合并 |
| 产品体验（打字感） | **无法离线测量**，需产品/用户侧确认 | 不确认 → **留档不做**（守卫优先级高于流式） |

**倾向结论**：A1 是唯一低风险形态，但其收益是体验而非延迟；**若 A1 的感知收益无法被产品侧确认（或实测 Δ≈0 被视为「无收益」），则留档不做**——这符合计划第 251-252 行的预设（「若 A 的感知收益经实测不显著，则留档不做」）。

### 5.4 守卫不变式（实施时的硬测试）

# P3-2 延迟预算校准（`turn_budget_seconds` / `max_react_steps`）

> 日期：2026-09-18
> 依据：本仓库实测探针 `app/scripts/probe_turn_latency.py`（本次新建）+ 代码取证
> 对应《能力补全全量计划.md》P3-2

## 一、问题（校准前的自述欠账）

`app/config/settings.py` 的 `turn_budget_seconds` 注释原文自述：

> 「待 T0 探针实测 P95 后按 `max_react_steps × P95 < turn_budget_seconds` 校准。」

该探针**从未落地**，值停在推理模型适配 T8 时抬到的 300s。对客服场景 300s 意味着
「一轮挂死 5 分钟才熔断」，与对照项目普遍秒级首响的预期严重不符。

## 二、探针设计

新增 `app/scripts/probe_turn_latency.py`：

- 从黄金集 `app/evaluation/cases_large.json` **按 `expected_intent` 分层抽样**
  （默认每层 2 例，确定性可复现）；
- 逐条经 `app/evaluation/sandbox.Sandbox` 真实运行，收集
  `RunTrace.llm_calls[*].latency_ms`（每次 LLM 调用的墙钟延迟，由沙箱插桩采集）；
- 输出总体与分意图的 P50/P95/max、实测 ReAct 步数分布、失败用例，并按
  `max_react_steps × P95 < turn_budget_seconds` 给出预算建议。

**为什么抽样而非全量**：全量 317 例在推理模型下单轮可达数十秒，成本与时长都不适合
作为常规探针；样本量与被抽中的用例 id 全部写进报告 JSON（`sampled_cases`），结论
按「样本口径」陈述。

## 三、实测结果

**样本**：12 例 / 30 次 LLM 调用，失败 0 条。被测模型 `DeepSeek-V4-Flash-0731`
（`.env` 的 `MODEL_NAME`），embedding 未参与本探针。

| 维度 | P50 | P95 | max | mean |
|---|---|---|---|---|
| 单次 LLM 调用延迟 | 3,738.7 ms | **10,047.6 ms** | 22,116.6 ms | 4,725.5 ms |

分意图（单次调用）：

| 意图 | n | P50 | P95 |
|---|---|---|---|
| complaint | 6 | 6,932.2 ms | 19,241.1 ms |
| greeting | 3 | 2,640.0 ms | 3,582.9 ms |
| order_query | 6 | 3,533.5 ms | 4,934.1 ms |
| product_consult | 5 | 3,481.1 ms | 5,553.9 ms |
| return_request | 5 | 3,042.8 ms | 5,994.5 ms |
| unspecified | 5 | 4,293.1 ms | 5,067.3 ms |

实测 ReAct 步数：P50 = 3、P95 = 3、max = 3（mean 2.5）。

**观察**：`complaint` 层显著高于其他意图（P95 19.2s）——投诉类输入触发更长的
思考与更多工具编排，是预算的实际约束层。

## 四、校准结论

按公式 `max_react_steps × P95 < turn_budget_seconds`：

```
8 × 10.05s ≈ 80.4s  <  120s   （约 1.5 倍余量）
```

**改动**：`turn_budget_seconds: 300 → 120`（`app/config/settings.py`）。
`max_react_steps` **维持 8**：实测最大步数 3，8 步已属宽松上界；收紧它反而可能
在复杂多跳/多工具场景逼出 ForcedFinalize，与验收要求相悖。

`llm_timeout_seconds` 维持 `.env` 的 60s（单调用实测 max 22.1s，约 2.7 倍余量），
不动。

**推理模型 profile 单独一档**：本校准即针对当前推理模型（DeepSeek-V4-Flash）。
换用非推理模型（`extraction_model` 那类快速模型）时单调用延迟通常降至数百毫秒量级，
届时 120s 会显得过宽——但预算过宽只损失熔断及时性、不损正确性，故不为此另设档位
（避免新增开关）。若将来切换主模型，重跑本探针即可。

## 五、验证与未验证（诚实边界）

**已验证**：

- 探针 12 例全部跑通、0 失败，说明 120s 预算下**本样本无一轮触发预算熔断**
  （若触发，`react_steps` 会表现为被截断且用例会带 `budget_fallback`/错误）。
- 全量单测通过（`pytest tests/unit`）——预算变更不影响单测口径。

**未验证（残留项）**：

- 探针样本量偏小（每层 2 例），`complaint` 层 P95 由 6 个样本点得出，置信区间宽。

### 五之二、全量 ForcedFinalize 回归（2026-09-18 补齐，D4）

> 上文「全量 eval 的 ForcedFinalize 率回归未跑」已补：335 例全量 agent 评测
> （`artifacts/eval/v2/d2-rules-final/`）在 **120s 预算**下实测：

- `forced_finalize` **0/335**、`error` **0/335**（逐例布尔标记全为 False）；
- 交叉证据：本文件 §三 的探针（单次调用 P95 = 10.05s、max = 22.1s）与实测最大
  ReAct 步数 3 → 单轮墙钟上界约 66s，远低于 120s。

**结论：预算收紧未逼出任何强制终答，不构成回归。**

**为什么不需要 300s 对照臂**：`forced_finalize` 是逐例布尔值，120s 臂已为 0。
否证只依赖「率非负」：命题「收紧导致强制终答上升」要求 rate(120s) > rate(300s)，
而 rate(120s) = 0 且任何率 ≥ 0 → 0 > rate(300s) ≥ 0 矛盾，命题不成立。
（机制口径：`forced_finalize` 由步数耗尽驱动，预算耗尽走独立的 `budget_fallback`
标记——本轮 `budget_fallback` 同样全为 0。）

**未做**：300s 全量对照臂（受 API 吞吐限制，单轮 335 例耗时数小时）。
如需补齐：`TURN_BUDGET_SECONDS=300` 注入 env 后重跑
`python -m app.scripts.run_eval_resilient --dataset app/evaluation/cases_large.json --no-judge`。

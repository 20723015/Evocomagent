前面九期小夕能查订单、调工具、检索知识库、多 Agent 协作、记忆、用技能，也有了评估体系证明自己没变差。但知识库里那四篇文档永远是手写的，客服回答里那些反复被问到的好问题，没人沉淀下来。这期给项目加 QA 自动沉淀：把真实对话里的优质问答自动变成知识库文档，Agent 用着用着自己变聪明

聊几个核心设计问题：



## 轮次是怎么「落盘」的

沉淀的原料是真实对话。我在 `chat.py` 和 `orchestrator.py` 的 `chat()` 里挂了一个 TurnRecorder：用户问题进来前记下标，结构化回复生成后、历史压缩前，把「本轮新增的消息切片」交给它解析——从 `tool_calls` 里找到 `search_knowledge` 的 `tool_call_id`，去 tool 消息里 `json.loads` 出命中结果，只留 `success=True` 的，连同问题、回复、意图、置信度一起脱敏后原子写入 `turns/YYYYMMDD/<turn_id>.json`

挂载位置是精心选的：在 `_compress_history()` 之前。历史压缩会把老消息丢进 summary，但 turn 已经落盘了，所以「压缩不丢候选」是结构上保证的，不用做任何额外处理。记录失败也只打印警告，绝不阻断客服主流程

session 文件顺手升到了 v2：加了 `session_id`，v1 老文件读出来是 `None` 就新生成一个，`tests/test_memory.py` 那种老测试只导入不调用 `save_session`，零破坏。v1 格式的 `session.json` 里躺着的旧对话也不浪费——miner 里有个 legacy 状态机，按 user 消息切轮次，处理正常轮次、多步工具链、双 assistant、损坏 JSON、孤立消息五种形态，坏了 JSON 就用原文降级，没有最终回答的轮次直接跳过



## 从 turn 到知识库，为什么要五层闸门

一条对话成为知识库文档，中间不能只有一个「值不值得存」的判断——那会把坑全踩一遍。我设计了五层闸门：

第一层是**规则闸门**，零成本先把明显不行的筛掉：置信度低于 0.8（模型自己都不确定）、要转人工的、没检索到任何来源的（没依据怎么当知识）、问题或答案太短/太长的（规范化后长度不合法）。PII 和注入检测也在这层——手机号、邮箱、身份证、带字段词的银行卡号和 18 位以上单号被替换成占位符，`system:` 开头的角色注入、忽略指令、代码围栏直接整条淘汰，政策数字（7天、12元）不被误杀

第二层是**预去重**：拿原始脱敏问题和整个知识库做向量检索，相似度过 0.95 直接丢——一个问答第一次被问是新闻，第一百次被问就是噪音。第三层是**价值 Judge**：LLM 判断这条候选值不值得沉淀，顺便把口语化问题改写成规范、可检索的表述。第四层是**接地 Judge**——这层是最有意思的

接地 Judge 干的事是「逐断言核对证据」：把检索来源里的人工文档片段喂给裁判模型，让它检查回答里的每个关键断言（数字、时效、政策条款）有没有证据支撑。注意证据集有个硬边界：`source_path` 以 `evolved/` 开头的来源——也就是自进化子目录里的自进化知识——**一律剔除**。为什么？自进化知识的来源又是自进化知识，那是「自证自答」，会越滚越偏。根目录人工文档与 `uploads/` 上传文档（v7 KB 文档上传链路）都有资格当证据；新的边界不是「不含 `/`」而是「不以 `evolved/` 开头」，否则上传链路的文档会被整批误杀、候选全部进 pending

第五层是**最终去重**：规范化后的问题+答案拼起来再检索一遍，过 0.9 丢掉；同一批候选里再两两互查，重复的保留质量分/来源分/置信度更高的一方

Judge 本身也要扛故障：结构化输出（`beta.parse`）失败降级成文本 prompt + JSON 解析，再失败返回 `failed=True` 只能进 pending 等人审——宁可慢，不可错。审批通过的候选走同一条发布链路，只是跳过 Judge



## 发布为什么做成「事务」

沉淀是写线上知识库，不能「写一半崩了留下一地垃圾」。所以发布链路每一步都有兜底：

1. 先拿**单写者锁**——`evolution.lock` 记 pid/hostname/started_at，同主机进程活着就拒绝，死了超过 7200 秒归档接管，跨主机只能 `--force-unlock`
2. 文档**移动前先写 journal**，记下 staging 文件清单和 staging 索引目标
3. 文档移进 `knowledge/evolved/`，构建**版本化索引**（`kb_index.<generation>.json` 或 `ecom_kb__<generation>` collection），但**不切换指针**
4. 全部验证（全新实例加载、模型一致、数量一致、chunk_id 唯一、向量探针 top1）通过后，才把 generation 指针切过去
5. 下次运行开始先恢复 journal：发现 generation 没切换，说明发布中断了，删掉孤立文档和 staging 索引，旧索引照常可用；发现已切换，就由 ledger 补记 published

「不激活就不切换」是整条链的安全底线：任何一个环节失败，指针都停在旧代，线上检索永远用的是一份完整可用的索引。运行中 Agent 的检索器每次搜索前读一遍指针文件（几 KB），generation 变了就重建单例，重建失败保留内存里 last-known-good 实例——热刷新 + 永不中断

`--with-eval` 是给正式环境上线的最后一关：先在活动索引上跑一遍第 9 期沙箱评测拿 baseline，staging 索引建好后把检索 override 指过去再跑一遍，还要做候选探针（原问题和规范化问题都必须 top3 命中自己那份新文档）。任何一个「原通过变失败」「通过率下降」「错误增加」「结果得分掉超过 0.02」或探针失败，就清掉 staging、退出码 2，报告里逐用例打 before/after 供人工判断是知识真变差了还是 judge 抖动

## 淘汰半边：知识会过期

「沉淀」只是前半——机器把对话变成知识；后半是「淘汰」：人工知识后来变了，旧沉淀的断言可能已经没依据、成了过时的坏答案。重接地（revalidate）补的就是这半边：人工知识变更（上传、下架、手工 CLI 重建都表现为 generation 切换）后，下次运行自动对存量沉淀做一轮核对——活动检索器按「问题」检索 top-8，命中映射成与 recorder 相同的来源，再喂接地 Judge（每条一次 LLM 调用）。顺序上缺 `effective_date` 的存量文档视为最旧、最旧优先，单次上限 `EVOLVE_MAX_REGROUND_PER_RUN`（默认 20）控制成本

核对通过 → 原地刷新 frontmatter 的 `last_validated`——frontmatter 不进 chunk，所以**不需要重建索引**，这是个便宜的路径。核对不通过 → 文档移 trash + 由 ledger 反查 candidate_id 进 pending（`revalidation_failed`），批量一次 build+activate（多条合并一次重建），新代里不再有它。隔离本身也是事务：移动文件前写 journal（`phase=revalidate` + 隔离清单 + 目标索引），激活后清除；中断了就**前进式恢复**——判定已经做出，恢复只前进不回退：清单里还在 `evolved/` 的完成隔离、已在 trash 的补账，再一次重建；要是发现目标代已经激活（崩在 activate 和清 journal 之间），说明账目早写完了，什么都不用做。什么触发？`state/last_human_generation.json` 记上次运行结束的活动代，当前代不同才执行；运行结束（包括失败）再把记录刷新为最终活动代——自己的发布/重建不会自我触发，`--revalidate` 可强制全量（仍受单次上限约束）

沉淀文档的 frontmatter 为此做了增强：`effective_date`（发布日 + `EVOLVE_EFFECTIVE_DAYS`，默认 180）、`grounded_on`（沉淀时的人工证据列表）、`quality_score`、`last_validated`。`effective_date` 让通用时效扫描（阶段六 6.4）对自进化文档自动生效——不再落入 unknown 提示补全

## 替换与运营

近重复的最后一个洞：新表述改进了旧答案时（比如补充了时效信息），旧的法子是把 ≥0.9 的命中一律按重复丢弃——新答案永远无法替换旧沉淀，变体各自积累反而稀释检索。现在最终去重返回的是**命中的 top1 + 命中侧**（而不是 bool）：**问题侧**命中 `evolved/` 旧沉淀、且新候选 `quality_score` ≥ 旧文档 frontmatter 的 `quality_score`（旧文档缺字段视为可替换）→ 标记 `replaces=<旧文件名>` 保留候选；答案侧命中和人工文档（根目录 / uploads/）命中维持丢弃——前者只说明回答模板化、问题可能完全不同，替换会误删回答另一个问题的旧沉淀；后者是机器沉淀永远不吞人工知识

替换走发布事务：journal 记录 `replaced_docs` → 旧文档移 trash（在索引 build 之前，新代只含新文档）→ 正常 build/activate → 成功后 ledger 旧条目 `unpublish_mark + move_to_trash` 清账。崩溃恢复两分支都覆盖：未切换 → 从 trash 还原被替换文档；已切换 → 补记循环幂等清账。报告带 `replaced` 计数，per_candidate 记录「published ·replaced:旧文件名」等状态

另外几条运营细节：with-eval 阻断的候选如今进 pending（`eval_blocked:<原因>`），而不是「不 mark processed 下轮重试」——后者在 temperature=0 下决策确定，会每轮全额烧 Judge 且结果不变；进 pending 后下轮被精确去重零成本跳过，人工凭 `-blocked` 报告的 before/after 审批。S3 后端（multi-pod）下 CLI 运行前会从 turns 归档同步（幂等缓存下载，游标只拉新增且只前进，最近 3 天的 key 不受游标限制——防时钟回拨的迟到写入，tmp+os.replace 原子写），S3 不可用直接 fail-closed 拒绝空跑——多 Pod 下 recorder 只写对象存储、矿工只读本地，不同步就是静默挖空。PII 模式也扩了：运单号、≥12 位裸长数字（无字段词的单号/流水号）、关键字邻近的联系方式（微信/vx/wx/qq 后缀 5-20 位、**不含连字符且必须含数字**的账号——"wx widgets"、"vx-miniapp" 这类普通词不误杀）都脱敏，政策数字（7天/12元）仍然不误杀

## 面试怎么讲

这期的核心叙事是「**一个把对话变成知识的闭环，怎么做到又安全又不会停**」：五层闸门各管一类风险（规则管成本、去重管噪音、价值管质量、接地管可信、复扫管合规），事务和 generation 管故障恢复，pending 把「机器判断」和「人工兜底」接起来。讲到「自进化知识不能当自己的证据」和「不激活就不切换」这两条原则时，面试官基本就能确认你是真做过而不是背概念。「知识会过期」和「近重复新答案能替换旧沉淀」是把闭环补完整的两块——面试官追问「沉淀进去的坏知识怎么办」时，重接地和替换就是答案

成本要主动提：Judge 每候选两次 LLM 调用（价值+接地），`EVOLVE_MAX_JUDGE_PER_RUN` 是每次运行的硬上限，dry-run 会先告诉你预计花多少 API 调用，灰度顺序是 dry-run 看量 → 只开捕获攒 turns → `--with-eval` 小步放 → 再开 `SELF_EVOLVE_ENABLED`
